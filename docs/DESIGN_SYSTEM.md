## 0.1 为什么换主色

v3.0 的 Indigo `#6366f1` 有两个问题：

1. **它是 Tailwind 的默认 indigo-500**，无数 SaaS 在用，辨识度低 —— 看不出这是旅行产品
2. **对比度不达标**：`#6366f1` 配白字只有 **4.47:1**，WCAG AA 要求 4.5:1，差 0.03；
   而当时用的是渐变 `#6366f1 → #8b7bf7`，后半段更浅、实际更低

换成深青 `#0e7490` 后：

| | 对比度 | |
|---|---|---|
| `#6366f1` 配白字（旧主色） | 4.47 : 1 | ✗ 未达 AA |
| `#0e7490` 配白字（新主色） | **5.36 : 1** | ✓ |
| 渐变最深端 `#155e75` 配白字 | **7.26 : 1** | ✓ |

渐变的两个端点**都做了核算** —— 刻意没做"深→亮"的大跨度渐变，
那种渐变的浅端配白字会掉到 3:1 以下（参考站本身的渐变就有这个问题）。

选深青而非珊瑚的另一个原因：珊瑚红会与**错误色 `#e34850` 冲突**，
红色既表示品牌又表示出错，语义会打架。

**两次作废的教训**：v1 走"安静"、v2 走"印刷感"，两次都是从**我的审美偏好**出发选方向，
而不是从用户已有的参照物出发。用户给出参考站之后，需求才真正清晰。
**下次遇到"想优化但说不清要什么"的情况，第一步就该问"有没有你喜欢的站"**，
而不是先提三个方向让他挑。

## 1. 令牌来源（重要）

这一版的色值**不是目测的**，是从参考站产物的 CSS 里提取的**真实自定义属性**。

```css
/* 圆角：这个风格的灵魂 */
--radius-xs: 6px;    --radius-sm: 8px;
--radius-md: 12px;   /* 输入框、小容器 */
```

## 4. 组件语言

| 组件 | 做法 |
|---|---|
| **主按钮** | 渐变药丸 + 同色柔光。hover 用 `filter: brightness(1.06)` 提亮（不换渐变色，避免跳变） |
| 次按钮 | 白底 + 浅描边 + 药丸；hover 换浅紫底 + 主色文字 |
| **输入控件** | 白底 + 1px 浅描边 + **12px 圆角**；聚焦时 **3px 半透明主色光晕环**（这套视觉最容易辨认的交互细节） |
| 卡片 | 白底 + 1px 浅描边 + 16px 圆角 + `--shadow-1`。**"浮起来的白纸片"** |
| 表格 | 浅灰表头（圆角顶角）+ 行间浅线，行 hover 浅紫底 |
| 标签 | 药丸 + 浅紫底 + 主色文字；语义类用对应的浅底 |
| 折叠面板 | 白卡 + 16px 圆角 + 轻阴影 |
| 浮层 | 16px 圆角 + `--shadow-overlay` |
| 状态点 | 圆点 + 同色浅底外发光环 |
| 导航当前项 | **浅紫底药丸** —— 这套视觉里"选中"的统一表达 |

## 5. 页面结构

### 首页

**三层结构**，不再是一张表单卡包办一切（这是用户明确要求的：「不要局限在一个卡片里」）：

```
┌─ 第 1 层：Hero + 起步区 ────────────────────────────────┐
│  [柔和紫色光晕（两个模糊圆，不铺满）]                      │
│                                                          │
│        [✦ AI 智能行程规划]        ← 浅紫底药丸小标签       │
│        想去哪儿，先说说你的计划     ← 居中大标题            │
│        描述目的地和天数，或从下面的热门攻略里挑一个。        │
│                                                          │
│     ┌──────────────────────────────────────────┐        │
│     │ 🔍 [国庆想去云南待五天，喜欢自然风光…] 📎 [开始规划 →] │  ← 白色大药丸
│     └──────────────────────────────────────────┘        │  + shadow-4
│                                                          │
│        热门 [北京][上海][成都][西安][杭州]  📤 上传截图/文件 │
└──────────────────────────────────────────────────────────┘

┌─ 第 2 层：热门目的地（下滑可见，带照片）──────────────────┐
│  热门目的地                        点一张卡片即可填入      │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐           │
│  │ [照片 16:10]│ │ [照片]      │ │ [照片]      │           │
│  │  ● 3 天     │ │  ● 2 天     │ │  ● 3 天     │           │
│  │ 北京  历史文化│ │ 上海  城市漫步│ │ 成都  美食   │           │
│  │ …描述…       │ │ …          │ │ …          │           │
│  │ 看看北京怎么玩→│ │ …          │ │ …          │           │
│  └────────────┘ └────────────┘ └────────────┘           │
└──────────────────────────────────────────────────────────┘
        ↓ 点「开始规划」/ 热门城市 / 攻略卡片
   跳转 /create（详情见下）
```

**城市照片来源**：`GET /api/poi/photo?name=<地标>`（后端接 Unsplash 关键词搜索）。
每张卡片的 `landmark` 字段就是取图关键词 —— 传**地标名**而不是城市名，
因为"北京"搜出来的图太杂（故宫博物院 / 外滩 / 大熊猫基地 / 兵马俑 / 西湖）。

三层降级，保证照片永远不是"必须成功"的：
1. 接口失败或返回空 → 用 `placeholderImage()` 生成的渐变块
2. 图片 URL 加载失败 → 换成浅色底占位，并置空 `onerror` 防止无限触发
3. `loading="lazy"` + 卡片先用占位块渲染 → 不阻塞首屏

> **⚠️ 关键词必须用英文 —— 这是踩过的坑**
> Unsplash 的搜索**对中文基本无效**。实测：
> 「外滩」和「西湖」返回**同一张图**；「成都大熊猫繁育研究基地」**直接搜不到**（返回空）。
> 换成英文词（`The Bund Shanghai` / `West Lake Hangzhou` / `Chengdu panda base`）后，
> **五个城市各拿到不同的、语义正确的图**。
> 所以卡片数据里有两个字段：`photoQuery`（英文，取图用）和 `landmark`（中文，只给 alt 用）。
>
> 顺带修了后端：`unsplash_service.search_photos()` 原来**没限定 `orientation`** ——
> 卡片是 16:10 横画幅，拿到竖图会被 `object-fit: cover` 裁得只剩中间一条。
> 现已加 `"orientation": "landscape"`。
>
> 注意：这个中文搜索的问题**同样影响结果页的景点配图**（那边传的是后端返回的中文景点名）。
> 那是既有行为，本次未动。

**首页只负责两件事**：让用户「说一句」或「挑一个」。详细的日期与偏好搬到了 `/create` ——
那些是"决定要去了"之后才需要填的东西，全堆在落地页会让它变成一个长表单。

#### 关联：创建页 `/create`

参考站的"对话式引导 + 点选式表单"。整页只有一张 640px 宽的白卡：

```
← 取消创建

                          ┌──────────────────────────┐
                          │ 国庆想去云南待五天，喜欢自然风光 │  ← 用户那句话（气泡，右上）
                          └──────────────────────────┘
   ┌────────────────────────────────────────────────┐
   │ 云南，好地方。先确认下面几项，我好把行程排得合你心意。 │  ← AI 引导文案（随城市变化）
   │                                                │
   │  目的地  [重庆              ]                    │  ← 不再放城市快捷选择（首页已有，重复）
   │  日期    [出发] → [返程]        共 5 天          │  ← 两个日期都能直接选
   │  偏好    [历史文化][自然风光][美食][…]            │  ← 多选，上限 3
   │  交通    [公共交通][自驾][步行][混合]             │  ← 单选
   │  住宿    [经济型][舒适型][豪华][民宿]             │  ← 单选
   │  补充    [textarea]                            │
   │                                                │
   │  ┌──────────────────────────────────────────┐  │
   │  │            生成我的行程                    │  │  ← 全宽渐变药丸
   │  └──────────────────────────────────────────┘  │
   └────────────────────────────────────────────────┘
```

**三处关键交互：**

1. **日期与天数双向联动**。点天数会推算返程日期；也可以**直接选返程日期**，天数跟着变。
   数据流是**单向**的：`travelDays` 由起止日期 computed 得出，它**不是可写字段** ——
   否则"点天数写日期"和"改日期算天数"会成为两个真相来源、互相覆写
   （典型症状：改了返程日期，天数还是旧的）。
   改出发日期时**保持行程长度平移**：9/17–9/21 改成 10/01 出发 → 10/01–10/05。
   已用脚本实测 5 个场景（改出发 / 点天数 / 改返程 / 超 30 天收回 / 清空出发）全部符合预期。
2. **选项全部用标签点选**，不用下拉框 —— 少一次点击，选项一眼看全。
3. **出发日期默认明天、天数默认 3**。不给默认值的话用户会被"请选择日期"拦一次，
   而绝大多数人不会当天出发；3 天则能装下"一座城 + 一个近郊"的经典结构。

> 实现细节：出发日期用 `:value` + `@change` 而不是 `v-model`。因为 `v-model` 会先把
> `start_date` 改掉，那时再想"按原天数平移"已经拿不到原天数（`travelDays` 已按
> 「新 start + 旧 end」算过一轮）。手动赋值可以先读旧天数、再一次性写好两个日期。
> 清空出发日期时**连返程一起清掉**，避免出现"没有出发日却显示着返程"的怪状态。

**从用户那句话里读出目的地与天数** —— 体验上最关键的一步：

用户在首页说过「我想去重庆玩五天」，如果创建页让他把目的地和天数**再填一遍**，
那就是纯粹的重复劳动。所以创建页会解析这句话（`utils/parseTripIntent.ts`），
并把结果**显式显示成标签**：

```
[重庆] [5天]   已从你的描述里读出 · 不对的话直接改下面
```

三条设计约束：

1. **保守预填，宁可漏不可错** —— 解析不出来就留空让用户手填，不会比原来更差。
   一个字面量解析错误比"没解析出来"更让人困惑。
2. **结果显式展示**，不悄悄改字段 —— 用户需要能确认"它读懂了"，
   而不是自己发现字段被改了却不知道谁改的。
3. **引导文案复述**：「重庆 5 天，记下了。再确认几个细节，我就开始排。」

覆盖的表达：`五 / 十 / 十五 / 二十八` 等中文数字、`5日`、`去X玩/待/看`、`想去X` 等结构。
**11 个用例实测通过**（含「随便走走」「上海」这类应当解析失败的反例，正确返回空）。

> ⚠️ 它是**规则匹配，不是语义理解**：
> 「想去云南，顺便去趟重庆」只会取到第一个地名；「5d」「五天左右」认不出。
> 想真正做到理解，需要后端用 LLM 解析（一次调用成本很低，但那是后端的工作）。

**两页之间的数据传递**：首页把「用户那句话 + 挑的城市」写进 `sessionStorage`（`tripDraft`），
创建页读出来回显成气泡。用 sessionStorage 而不是 URL query —— 描述上限 200 字，
塞进地址栏既难看又有长度限制，而且刷新后草稿还在。

**上传功能目前只做前端展示**（在首页）：可以选中文件、显示文件名、清空，但**不上传**。
后端没有接收文件的接口。要真做需要先加一个解析接口。

**攻略卡片是静态占位**：点击把城市名带到创建页。

### 结果页

**结构：Tab 分页 + 右侧常驻地图。** 参考产品给的方向——不再是一张长页面，而是
「总览 / Day 1 / Day 2 …」各自一页，左内容、右地图。

```
┌──────────────────────────────────────────────┐
│ 总览 │ Day 1 🌤 │ Day 2 │ Day 3        ← 吸顶 │
├───────────────────────────┬──────────────────┤
│ 左：当前页内容              │ 右：地图常驻      │
│  · 总览 → 城市/预算/一览/    │  · sticky 全高    │
│          天气/知识出处       │  · 切 Tab 时      │
│  · Day N → 时间轴/住宿/餐饮  │    聚焦到那一天   │
└───────────────────────────┴──────────────────┘
```

页签记在 `?day=N` 上（不写 = 总览）。切页用 `router.replace` 而非 `push`：
不写历史记录，否则 5 天的行程要按 5 次返回才走得掉。代价是"返回键 = 离开行程"
而不是"退回上一个 Tab"——这是刻意的取舍。

**三个位置必须对齐 `--header-h`**，否则会被全局顶栏（`z-index: 100`）盖住：
吸顶的 Tab（`z-index: 20`，要压住地图但不能越过顶栏）、sticky 的地图、
以及地图的高度预算。Tab 栏高约 53px，抽成 `--tabs-h: 56px` 复用。

**地图高度的历史（三次迭代）：**

| 方案 | 结果 |
|---|---|
| 并排 + `align-items: flex-start` | 左栏高于地图时，**地图下方留白** |
| 并排 + `align-items: stretch`（等高） | 留白没了，但**地图被左栏拉长** —— 概览里的"建议"是 LLM 生成的，长度随机，地图就跟着变成一条竖长条 |
| 通栏 + 固定高度 | 两侧互不依赖了，但地图跑到页面下方，和内容脱节 |
| **右侧常驻 + sticky（当前）** | 宽度固定比例、高度按视口算，切页自动聚焦 |

> **教训：「消留白」不要靠「让两边高度相等」。** 等高只是把问题从"下方留白"
> 转移到"另一侧被拉长"。正确做法是让两侧高度**互不依赖**。

```css
.rc-body  { display: grid; grid-template-columns: minmax(0, 1fr) 42%; }
.rc-map   { position: sticky; top: calc(var(--header-h) + var(--tabs-h) + var(--space-4)); }
.map-box  { height: clamp(360px, calc(100dvh - var(--header-h) - var(--tabs-h) - 220px), 720px); }
```

**≤991 地图不再常驻**：横向排不下两块内容，改成「Tab → 地图 → 内容」纵向，
地图回到固定高度 320px（≤767 为 260px），`order: -1` 让它排在内容上方
——先看空间关系，再看文字。

#### ⚠️ 分页带来的两个副作用（都已处理）

| 副作用 | 处理 |
|---|---|
| **导出失效**：`usePlanExport` 抓 `.plan-capture-root` 的 innerHTML，分页后那就只有当前一页，导出 PDF 只会得到 Day 2 一页 | 导出时临时挂一份离屏的「完整行程」视图（`captureMode`），抓它、抓完卸掉；日常渲染不多一份 DOM |
| **Tab 滚出视口**：Day 1 内容一长，切天得先滚回顶部，分页的意义就没了 | Tab 栏 `position: sticky`，背景给实色（否则内容从下面透出来） |

离屏视图用 `position: fixed; left: -20000px` 而不是 `display: none`——后者量不到
尺寸，html2canvas 会截出 0×0 的空白图。它里面的地图位用 `data-export-map`
而不是 `id="amap-container"`：真实地图已经占了这个 id，**同 id 两个容器**是隐患
（`getElementById` 谁先谁后没有保证）。

### 背景光晕的做法

用两个 `filter: blur(80px)` 的模糊圆做**局部**点缀，透明度 0.24–0.28。
**不铺满整屏** —— 铺满就变成烂大街的"紫渐变背景"，而局部光晕才是轻盈感的来源。
手机上模糊半径降到 60px 且缩小尺寸，避免大面积 blur 影响滚动帧率。
